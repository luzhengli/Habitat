# 10 · 原型先行与高保真还原合同

## 用户最新目标与本轮边界

用户反馈：当前实现与提供的原型差别很大；目标是高保真、像素级还原。后续涉及界面或交互修改，必须先修改原型，确认没问题后再基于原型实现。

这项要求覆盖此前“只保留 Air 风格”“生产 tokens 为权威”及以功能测试/浏览器可用性代替视觉验收的做法。当前已有真实后端与工程基线继续使用；本轮目标是纠正前端还原，不重建项目、不换品牌、不重选视觉方向。

本文件定义长期规则；当前进度见 PLAN/tasks.json，候选版本与批准范围只查 design/prototype-baselines.md。

## 哪份材料有决定权

- 现有已认可原型：`reference/air/Habitat-Air.html`，配套结构/样式参考 `reference/air/src/`；视觉证据为 `design/01–12` 原始 PNG。
- 原始材料保持不变，作为可追溯基线。必要修改在 `design/prototype-revisions/<revision>/` 创建独立、可运行候选，附对应源码或可重建说明。
- 基线登记见 `design/prototype-baselines.md`。只把用户明确确认的具体版本/页面/状态提升为有效基线；Git 提交、Agent 自检、测试通过和用户未回复都不构成确认。
- 同一状态的 HTML、源码、PNG 若不一致，先标明差异与来源；不能挑最接近当前实现的材料充当基线。用可审阅原型解决冲突并取得用户确认。
- `apps/web` 和旧实现截图是被比较对象，不能反向定义设计。禁止为了降低差异而改原型来迁就已经写出的 UI。
- 文档约束功能真实性与安全；已确认原型约束可见布局、内容层级、组件、文案和交互。二者冲突时记录差异，先提出原型修订，不暗中牺牲任意一方。

## 长期工作顺序

### A. 已确认原型的忠实还原

目标页面/状态已明确且无需设计变更时，可直接将生产界面还原到该基线，不重复要求用户确认原有设计。修改 CSS/组件以缩小与原型的差异，属于还原工作。

### B. 需要改变设计或补充状态

任何新增、删除、移位、合并、简化、文案调整、信息层级/导航/表单/抽屉/弹窗/状态反馈变化，或原型未覆盖的真实错误/权限/能力状态，都必须：

1. 列出需求与受影响页面/状态，解释现有原型为什么不足。
2. 先在独立原型候选中实现修改，提供可点击预览、前后截图和变更清单；同步 desktop/Web、窄窗口及必要状态。
3. 请用户审阅并明确确认该版本。确认前不把候选设计接入生产页面；可继续不依赖该确认的测量、已有原型还原和后端回归。
4. 记录确认来源、版本、页面范围和文件 hash/commit；再按该版本像素级还原并做对照验收。
5. 实现时又发现需要改设计，返回步骤 1，不在生产代码中先自行决定再补原型。

“确认没问题”指用户确认，不是 Agent 自行判定。此确认门槛来自本次用户明确要求。纯后端且不改变可见行为的修复不要求制造原型变更；仍须守住安全合同并测试。

## Web 适配不能成为近似还原的理由

继续使用 React Web + 本机服务，不恢复 Tauri/Electron 或伪造桌面行为。原型中的桌面标题栏留白、拖拽区、Mac 快捷键、原型徽标等需要 Web 适配时，先在候选原型中体现具体变化并请用户确认。此前允许移除桌面占位的文字说明不等于已确认新的页面坐标与布局。

除已确认的 Web 适配外，保留导航、最近项目、筛选/标签、卡片内容层级、详情分页、工具选择、项目表格/开关、草稿栏、确认摘要、诊断/更新/历史/设置的完整设计结构。不能以“核心功能能用”为理由替换成简化表单、复选框列表或大段技术说明；具体差异必须实测，不能把这些示例当作已完成的审计。

不支持的真实能力保持禁用/未知/清晰错误，但其展示方式先纳入原型。原型可以使用明确标注的演示状态；生产必须来自真实 API。不能把演示模型、模拟事务或前端历史快照导入生产，更不能为凑齐画面伪造成功。

## V0–V3 顺序与产物

| 阶段 | 工作 | 退出条件 |
|---|---|---|
| V0 基线与差异盘点 | 读合同，实际打开原型与当前应用；建立逐页逐状态映射、测量值和差异清单 | 可复现的双侧截图；每项差异标明直接还原/需原型修订/功能或环境缺口；未凭颜色相似判通过 |
| V1 原型修订与确认 | 对 Web 适配、缺失真实状态或必要产品变化制作独立候选 | 用户明确确认具体版本；无设计变更的页面可记录“不适用”并引用既有基线，不虚构确认 |
| V2 高保真实现 | 按已确认基线逐页恢复结构、组件、样式与交互，接回真实 API | 所有范围页面完成实现与本页对照；保留真实业务、安全、URL、草稿与恢复链；未获确认的候选不落生产 |
| V3 对照验收与回归 | 同条件截图/diff、浏览器交互与功能回归；集中展示结果给用户 | 下述视觉门槛通过、无未解释差异、测试/build 通过并取得用户最终视觉验收；再关闭 M4 |

每页按“原型 → 测量 → 必要的原型修订/用户确认 → 还原 → 同条件比较 → 修复”推进。不要把全部页面先做成近似版再统一宣称完成。确认只针对真实设计变化及最终视觉验收，不在每个已批准页面完工后重复请求开工许可。

## 必须覆盖的页面与状态

建立 `verification/fidelity/coverage.md`，逐项关联原型文件/版本、页面入口、状态、视口、fixture、生产截图、差异证据、结论及待确认项。至少覆盖：

- 全局壳：品牌、侧栏/最近项目、工具栏、导航选中与页面滚动。
- 技能库：有数据的标准两列卡片、原型已有的列表/标签/筛选/收藏、空库、搜索无结果、范围不完整。
- 技能详情：默认概览、使用位置、文件/版本及技术详情展开、固定标题与底部动作。
- 添加：添加 Skill/来源选择、授权表单、确认、取消、错误；原型没有的真实分支先补原型。
- 项目：项目选择、默认工具、本项目配置/其他范围、技能行/开关、添加选择、草稿栏。
- 变更确认：添加/移除/更新的数量、物理影响、继续编辑/确认、执行中/成功/失败/恢复。
- 需要处理：诊断列表与细节、范围解释；全局影响保持真实能力边界，不实现无授权的一键全局修复。
- 更新：完整包差异、个人修改、受影响项目和固定版本回退。
- 操作记录、撤销确认、设置；长中文、长路径、多变体及不能回滚状态。
- 键盘焦点、Tab/Esc、焦点恢复、IME、disabled/loading、reduced-motion。

原型出现但生产缺失的区域不能略过。逐项标明已实现、待实现、需原型修订或真实阻塞；不得以仅比较当前已有的少数控件缩减验收范围。

## 像素级对照方法与通过标准

1. 在同一操作系统/浏览器、相同 CSS 视口、DPR、100% 缩放、字体与加载完成条件下比较。固定滚动位置、交互状态、动画时刻、条目数量/顺序、文本长度、选择项和展开项。
2. 视口至少 1440×960、1280×820、960×640；390px 为可读兜底，不能代替桌面高保真。新响应式行为同样先落到原型并确认。
3. 用合成 fixture 经真实服务建立可比业务状态，保存创建/清理方法和内容映射；不扫描真实技能凑数，不在正式路由注入 mock。路径、时间等不可完全一致的真实内容单独列出，保留同等长度/布局影响的验证。
4. 为每项保存原型与实现的原始截图、并排图、透明叠加或像素 diff，以及测量记录。证据放在 `verification/fidelity/<baseline>/<page-state>/<viewport>/`；不得生成假截图、缩放错位后比较或编辑截图隐藏差异。
5. 测量侧栏/工具栏尺寸、内容起点、网格列/间距、卡片宽高、padding/margin、文本基线/换行、字号/字重/行高、颜色、边框/圆角/阴影、图标形状/尺寸/位置、抽屉/弹窗/底栏与滚动区域。
6. 同条件下可控的几何尺寸按 CSS 像素一致；无未解释的布局、结构、文字层级或交互差异。字体抗锯齿等平台噪声可以单列证据，不得把错位、缺控件、文案折行或尺寸偏差整体归为“渲染差异”。不能靠单一总差异百分比掩盖局部重大差异。
7. 确有例外时必须逐项说明依据与影响并获得用户确认；未确认/未修复的实质差异保持待办，不自授“足够相似”豁免。
8. Chromium 与真实 Safari 分别验收关键页面、焦点和滚动。同浏览器内与原型比对，不要求跨浏览器截图字节相同。保留 `npm run check` 和必要真实端到端回归；像素相似也不能替代操作安全验收。

## 状态与证据纪律

开发过程的并行拆分、模型/思考强度与写入所有权统一遵守 AGENTS.md 的 Orchestration 合同。子代理不能代替用户确认；浏览器状态与最终截图采集指定单一负责人，代码/fixture 版本稳定后再取证，避免将并行变更期间的画面混为同一次验收。

M0–M3 的工程结果保留为历史功能基线。M4 的 WEB-15 视觉验收重新打开；旧截图、52 项测试、浏览器可用性证明不能认定用户已经认可视觉效果。

阶段状态与下一步统一维护在 PLAN/tasks.json，不在本合同叠加会话检查点。最终用户视觉验收前不得写“无待办/全部完成”；历史工程通过不改变这一门槛。
